# Этапы 1–3 — отложенные пункты для следующих этапов

Итог ревью этапов 1–3 (per-task + финальное). Всё ниже осознанно не сделано;
каждый пункт привязан к этапу, где он становится важен.

## Закрыто на этапе 3 (LLM-оценка)

- Переоценка отсеянных прошлых версий правил — `aijobradar rules recheck`.
- Промпт `config/prompts/score-v1.md` явно просит проверить по описанию гео, резидентство,
  допуск, офис/гибрид и страну работодателя (ось `geo_eligible`, `employer_country_excluded`).
- Ключ кэша оценки и «не платить дважды» — частичный уникальный индекс по `status = 'ok'`.
- Остаточный риск правил по заголовку («Developer for US Only Portal» → «US only») не изменился;
  страховка — выборка в `review_queue`.

## Решения этапа 3, расходящиеся с планом

- Уточнение 2 плана: в `max_attempts` засчитываются только ответы модели, которые не прошли
  (`invalid_output`, включая исчерпанные повторы structured output у самого CLI, и `refused`).
  Ошибки среды (таймаут, старый CLI, HTTP-ошибка API) вакансию не откладывают — иначе один
  прогон со сломанным CLI навсегда отправил бы очередь в `score_failed`.
- Очередь оценки идёт от новых вакансий к старым (`posted_at`, затем `first_seen_at`), чтобы
  дневной бюджет уходил на свежие. Устаревание вакансий в `pending_score` повторно не
  проверяется: старые просто ждут в конце очереди.

- «Не платить дважды и не терять оплаченное» — гарантия штатного пути, не абсолютная. У
  `claude -p` нет ключа идемпотентности. Каждый ответ пишется сразу по приходу; при ошибке БД
  запись повторяется, а если БД не принимает результаты, дальнейшие вызовы не делаются.
  Остаточные окна: падение процесса между ответом и коммитом, таймаут или не-JSON после
  фактически выполненного запроса — такая вакансия будет оплачена ещё раз. Закрыть их можно
  только журналом stdout вне БД; в эфемерном CI этапа 4 он бесполезен.
- Лимит стоимости — мягкий: проверяется перед волной, одна волна (до `parallelism` вызовов)
  может его превысить.

## После этапа 3 — оценка

- **Первые живые прогоны:** `rules recheck` на dev-БД вернёт в `new` все отсевы прошлых версий
  правил; следующий `run` отправит прошедшие правила в очередь — первые прогоны гнать с `--limit`.
- У вакансии, оценённой из кэша или как «близнец» одинакового текста, нет своей строки
  `llm_scores`: оценку искать по ключу (`input_hash` + версии), не по `job_id`. Для выборки
  этапа 4 нужно решение: строка `status = 'cached'` или ссылка `jobs.llm_score_id`.
- `score_failed` окончателен для вакансии, хотя отложение считается по ключу: после смены
  `prompt_version`, модели или профиля отложенные не переоцениваются. Нужен `--retry-failed`.
- Расширение гео возвращает только `rejected`; `scored` с `geo_eligible = no` и `score_failed`
  остаются как есть.
- Downgrade 0003 оставляет вакансии в `scored`/`score_failed` без строк оценок.
- Записи `review_queue` у вакансий, возвращённых `rules recheck`, не удаляются: будущий просмотр
  очереди должен фильтровать по `jobs.state = 'rejected'`.
- Белый список окружения для `claude -p` (сейчас убирается только `ANTHROPIC_API_KEY`;
  `DATABASE_URL` наследуется, но у модели нет инструментов).

## До этапа 4 (GitHub Actions + Neon)

- **Himalayas:** сделано — `search?sort=recent`, окно 30 часов, ~300–350 страниц за прогон
  (~6 минут), лимит 500. Остаётся риск нарушенного порядка между страницами: если страница целиком старше
  окна, а на следующей есть свежая запись, обход остановится раньше. Если cron опоздает больше
  чем на 6 часов запаса или пропустит день, вакансии Himalayas за разрыв молча потеряются —
  на этапе 4 брать окно от времени прошлого успешного прогона.
- **Himalayas, 429.** 2026-10-09 один прогон на 300 страниц прошёл без ограничений, а второй
  подряд (~440 запросов за ~20 минут) получил `HTTP 429` на странице 142 → честный `degraded`.
  Лимит не опубликован. Если 429 начнёт приходить в ежедневном прогоне, добавить повтор с
  `Retry-After`/backoff.
- Тест CLI `fetch`: User-Agent/таймаут доходят до клиента, коды выхода по матрице §6.7.
- Публичные логи: ошибки уровня fetch (`describe_error`) — в одну строку и без сторонних значений;
  первая строка сообщения psycopg для некоторых ошибок может содержать входное значение.
- Нет `DATABASE_URL` → сейчас трейсбек pydantic; нужно понятное сообщение на русском.
  То же для `config/sources.yaml` и для `PermissionError`/`UnicodeDecodeError` при чтении
  профиля и правил (содержимое не печатается, но трейсбек в публичном логе).
- `config/rules.yaml`: испорченный regex (`re.error`) даёт трейсбек вместо кода 2; у
  `stale_days`, `rate_margin`, `review_sample_size` нет границ (ревью судьи этапа 2, P2).
- В `config/rules.yaml` маркеры страны работодателя есть только для одной страны — по
  публичному конфигу видно, какую страну исключает владелец. Принято; при желании добавить
  нейтральные наборы.
- Миграции гонять через direct-эндпоинт Neon, не `-pooler`.
- Защита тестовой БД проверяет только имя `*_test` — удалённая база с таким именем будет очищена.
- Этап 3: `score` завершается кодом 0, даже если все вакансии упали (`partial`) — для cron
  нужен сигнал (код или алерт в Telegram). При падении посреди оценки `runs.counts` теряет
  `llm_*` (строки `llm_scores` при этом сохранены); Ctrl+C оставляет прогон без `finished_at`.
- Два одновременных `score`/`run --score` (cron + ручной) оплатят одни и те же вакансии; второй
  `ok` упрётся в уникальный индекс → ложная `error`. Лекарство то же — advisory lock.
- Advisory lock / `concurrency` против одновременного локального и cron-прогона. С этапа 2 два
  одновременных `run` ещё и проверят одни и те же вакансии `new` дважды. Кроме
  конфликта уникального индекса: два прогона с разными source ID одной вакансии создадут два
  `jobs`, а параллельное расширение гео может потерять одно из обновлений.
- Лимит размера HTTP-ответа (JSON/XML/HTML) против memory/CPU DoS со стороны источника.
- Закрепить экшены CI на SHA, когда в workflow появятся секреты.
- Тест на враждебный XML (billion laughs / внешняя сущность) → источник `failed`, не падение.

## Когда понадобится источник, которому это важно (RemoteOK, v2 ATS)

- `canonical_url`: URL без схемы превращается в мусор; порт по умолчанию не убирается;
  `_DROP_PARAMS` выкидывает общие `source`/`src`/`u`.
- URL-шаг дедупа игнорирует компанию (общая страница карьеры склеила бы разные роли).
  Две разные вакансии одной компании с одинаковым заголовком за 60 дней всегда склеятся.
- `fetch_feeds` вызывает `key()` вне per-feed `try`; записи без id/guid схлопываются в один ключ.
- Himalayas: разбор страницы 2+ вне `try`; страница без `pubDate` останавливает обход;
  «все смещения» по усечению `int()` — эвристика (точная проверка: `set(range(-11, 15)) <= set(offsets)`).
- Himalayas: при смене формата (`parentCategories` пропал) источник покажется `empty`, а не `degraded`.

## Косметика / тесты, по случаю

- Стоп-слова из 2 букв («in», «of», «qa») считаются маркерами → «Engineer in Test» и
  «Engineer Test» не склеятся (консервативно, намеренно).
- Не все формы гендерных пометок убираются («(m/w/divers)», «[all genders]») — только пропуск склейки.
- WWR: навыки делятся по голому « and » («Machine Learning and AI» → два тега).
- Недостающие тесты: `make_engine`, round-trip `%` в `alembic_config`, downgrade, дробные
  смещения часовых поясов, смешанные даты в lookback, `call_count` в тесте нескольких индустрий Jobicy.
- Нет `server_default` у NOT NULL колонок (важно только для не-ORM писателей); нет индекса на
  `source_runs.run_id`.
